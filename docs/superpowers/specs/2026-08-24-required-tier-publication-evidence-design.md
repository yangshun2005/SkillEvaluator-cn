# 必需层级发布证据设计

## 问题

`BenchmarkReporter` 的 Tier Status 表显示 Tier 1 或 Tier 2 未运行时，仍可能推荐发布。总体结论只检查传入的结果，并对 Tier 3 有一条特殊的完整性规则，但没有对其他发布必需层级的缺失建模。公开基准 linter 只校验 Tier 3 一致性，重复了同一缺口。

## 发布契约

- Tier 1 始终必需。缺少非跳过 Tier 1 证据的卡片为 `INCOMPLETE`。
- Tier 2 默认必需。只有显式持久化的 `benchmark_policy.tier2_required = false` 才使缺失或干净跳过的 Tier 2 证据变为可选。
- Tier 3 保持当前默认必需策略和 `benchmark_policy.tier3_required = false` 逃生开关。
- `--no-dedup`、`--tiers 1,3` 等运行选择标志不是发布豁免。分层 CI 使用相同选择器，据此推断豁免会保留原缺陷。
- `--no-block-on-dedup` 只改变进程退出闸门，不会让 Tier 2 对发布变为可选。
- 无效策略值不能豁免必需证据。每个策略键按来源优先级独立解析：先看重复的 agent-evaluation 载荷与摘要声明，再看对等结果元数据。两份重复声明均为有效布尔值时必须一致；冲突时解析为必需证据。无效条目不视为值；某层级没有有效布尔值时落到下一较低优先级来源，任何位置都无有效值则视为必需。对等结果共享同一优先级，因此冲突布尔值无论聚合顺序如何都解析为必需证据。
- Agent-evaluation 策略声明绑定目标。不同 skill 的载荷或摘要不能豁免当前报告的证据，包括该外部 Tier 3 结果是干净的咨询性跳过时。
- 每个参与发布的结果都通过带版本的 `publication_target` 绑定到一个精确源快照。摘要覆盖规范化后的作者自有路径、节点类型、可执行位和文件内容，包括作者编写的 `evals/` 输入。带版本的配方只省略其枚举的生成路径：任意深度的 `.git`、`.venv`、`__pycache__` 和 `node_modules`；根目录生成的 state/result/version 目录；`evals/results`；以及三个生成的根发布文件。文件系统别名按实际文件系统身份处理，同名嵌套作者文件仍被覆盖。Tier 3 agent 可见投影共享此排除契约。生产者扫描在任意深度跳过生成产物名称，因此 Tier 1 运行会记录其跳过的根目录下任何已认证路径，发布保持 INCOMPLETE 直到该路径被重命名。实际添加链接/完整仓库上下文的 Tier 3 投影在运行时上下文拥有自己的带版本身份前不能认证发布；即使仓库根是目标，完整模式选择也可能依赖被排除的 Git/操作者状态。外部引用或工作区 skill 有相同限制。运行仍可用，但带有源身份冲突且为 `INCOMPLETE`。摘要缺失、格式错误或不同时，即使可见目标名称匹配，发布也为 `INCOMPLETE`。
- 完成的 Tier 3 证据在载荷和摘要中都携带其运行自有的 `run_id`。运行器在执行边界持久化目标身份；报告器绝不从当前实时路径回填。
- 通用逐结果 `optional` 元数据不能豁免发布必需的校验器。只有解析后的 `benchmark_policy` 能让 Tier 2 或 Tier 3 可选；Tier 1 始终必需。
- 可选证据存在但格式错误或不完整时不能认证发布。

## 组件与数据流

1. 共享发布评估解析 `tier2_required` 和 `tier3_required`，校验 Tier 1/Tier 2 执行证据，分类 Tier 3 完整性，并将发布状态与进程状态分开。`BenchmarkReporter` 渲染该评估，并在 Evaluation Metadata 中渲染两项要求。
2. 层级分类使用一个共享校验器名称分类器，使基准报告器和 HTML 报告器一致认为 `Similarity Check`、`Context Optimization` 等名称属于 Tier 2。
3. `JSONReporter` 保留解析后的发布策略以及显式 `publication_status` 和结构化 `publication` 详情，使外部聚合器不会把成功的进程闸门误认为发布完整性。逐结果源身份仍可用于拆分作业聚合。
4. `check_public_benchmarks.py` 解析全部三个层级行。对 PASS 卡片，它要求 Tier 1 完成、Tier 2 完成（除非显式可选）、Tier 3 完成（除非显式可选）。缺少 Tier 2 策略元数据时默认为必需，使较旧的矛盾卡片失败关闭。
5. Tier 1 和 Tier 2 生产者在检查前后比较源快照。Tier 3 在 `result.json` 中持久化源身份和运行 ID，并通过载荷、摘要、JSON、HTML 和 BENCHMARK 元数据传播。源变更冲突以有界通用标记传播，不泄露原始路径/摘要细节，也不在重渲染时消失。
6. 文档和变更日志说明执行选择、CLI 退出闸门和发布完整性是独立契约。

生成公开卡片的下游 CI 聚合器不在本仓库内。此变更给该聚合器提供失败关闭的源/运行绑定；部署特定的产物传输仍是单独的集成证明。

## 考虑过的替代方案

### 始终要求 Tier 2，无覆盖

简单，但移除了现有的持久化发布策略例外模式，且未给目录所有者明确的迁移路径。

### 从 CLI 选择推断 Tier 2 可选性

保留当前部分运行 PASS 卡片，但也把分层作业视为发布完成。这正是 issue #73 描述的失败。

### 显式持久化必需层级策略

这是选定设计。它区分运行了什么、什么影响进程退出码、发布需要什么证据。

## 错误处理与兼容性

- 现有程序化 Tier 1 + Tier 3 调用从 PASS 变为 INCOMPLETE，除非显式持久化 `tier2_required = false`。
- 没有 Tier 2 策略行的现有卡片被解释为要求 Tier 2。Tier 2 完成的好卡片仍有效；矛盾的 PASS 卡片无效。
- 现有 `tier3_required` 策略行为不变。
- 没有源身份的旧结果和没有运行 ID 的已完成 Tier 3 结果仍可读，但不能认证发布。
- 一等 CLI 或 YAML 发布策略选项有意不在范围内。元数据注入仍是编排逃生开关。

## 验证

- 证明报告器回归在生产变更前为红、之后为绿。
- 覆盖缺失 Tier 1、必需和可选 Tier 2、跳过/不完整 Tier 2、无效策略值，以及 Tier 2 校验器名称分类。
- 针对必需、可选、伪造和旧卡片覆盖发布 linter。
- 用 `--no-dedup`、`--tiers 1,3` 和 `--no-block-on-dedup` 运行 `validate`，证明 CLI 执行和退出语义保留，同时发布卡片失败关闭。
- 验证同一结果集生成的 BENCHMARK、JSON 和 HTML 输出。
- 将来自一个未变更源的拆分层级结果合并作为阳性对照，然后在作业之间更改作者自有文件，验证发布变为 `INCOMPLETE`。
- 运行聚焦测试套件、已提交卡片闸门、Ruff、包构建和完整默认测试套件。
