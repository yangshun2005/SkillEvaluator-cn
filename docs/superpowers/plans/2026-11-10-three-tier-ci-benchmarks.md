# 三层 CI 网关与基准测试实施计划

> **面向代理型工作者：** 使用测试驱动变更和独立审查。勾选已完成任务；将提供商凭据排除在报告和源代码管理之外。

**目标：** 提供轻量消费方 CI，运行 LLM 增强的 Tier 1、Tier 2 去重、通过可配置网关配对的 Claude Code/Codex Tier 3，并发布与源绑定的基准卡片及合并报告。

**架构：** 扩展共享编排和现有原生报告 API。将原生代理模型与评估器/评判模型分离。从保留的类型化证据生成基准卡片，不调用模型，也不在发布器中执行消费方代码。

**技术栈：** Python、GitHub Actions、GitLab CI、现有 SkillEvaluator 报告器和来源验证。

**规范：** 本聊天中用户批准的三层接入计划，以及后续对 Tier 1 `--llm`、网关支持的 Claude/GPT 代理、参考流水线独立的评估/报告/发布阶段，以及 `BENCHMARK.md` 发布的要求。

## 全局约束

- 仅 Tier 1 阻塞 CI。Tier 2/3 在所有报告和适配器中保持建议性质。
- Tier 3 支持 Docker 和本地，对每个选定的代理/用例提供完整的处理/基线覆盖。
- 保留两个轻量消费方入口文件；不复制脚本、不捆绑 wheel、不构建消费方镜像。
- 通用网关设置保留在 OSS 中；不提供内部端点、模型授权或凭据默认值。
- 对 Fork 和未授权/过期提交保持无密钥扫描。在暴露凭据前，授权并复查提供商支持的工作。
- 报告保留 14 天，包括失败/不完整的证据。绝不从建议性 CI 门禁推导发布资格。
- 固定评估器/运行时/工作流/工具版本。将候选编排的验证与关于已发布/最新 main 运行时支持的声明分开。
- 绝不发送 Slack 消息或手动重写机器人结果评论。

## 审查重点

- 缺失或矛盾的 Tier 1 必需检查声明必须经受 JSON 往返并保持不完整。
- 缺失的层级/代理/基线证据绝不能成为通过的基准。
- 多个技能和重排序的层级行必须按精确技能标识组合，而非按序号。
- 通用网关密钥/基础 URL 必须仅到达选定的提供商，绝不继承 CI 反馈凭据。
- 基准发布必须拒绝过期/Fork/外部证据，且不得导致被评估的源 PR 循环自我更新。
